# 07 · UI

原则同 pi-bettertui：信息密度优先，运行中只露最有用的一两行，结束后折成一行，展开才看全文。

主要使用场景是**全屏模式**（alt-screen），所以鼠标点击是一等交互；键盘路径同样完整，普通模式下也能用。

| 界面 | 归属 | 阶段 |
|---|---|---|
| `agent` 工具卡片（§1） | pi-subagent | Phase 1 |
| 通知消息（§2） | pi-subagent | Phase 2 |
| HUD 里的 agent 行（§3） | **渲染在 pi-hud**，数据和行为在 pi-subagent | Phase 2 |
| 键盘焦点：↓ 选中 agent 行（§4） | pi-subagent | Phase 2 |
| 鼠标点击 agent 行（§5） | pi-hud 捕获点击，pi-subagent 处理 | Phase 2 |
| 详情浮层（§6） | pi-subagent | Phase 2 |
| `/agents` 命令（§7） | pi-subagent | Phase 1（`types` / `reload`）、Phase 2（列表） |

**选择列表在底部，长内容详情用浮层。** 选择列表（`/agents` 列表）用不带 `overlay` 的 `ctx.ui.custom`，放在编辑器的位置，
和 pi 自己的选择器、bg-shell 的 `/background` 面板一样：列表短，应该让上面的对话保持可见。详情内容长，需要有上限的高度、自己滚动、
接收滚轮，所以用浮层（`overlay: true`）。浮层可以叠在列表上面：pi 关闭浮层时把焦点还给打开它之前的组件（也就是列表），
所以从列表进详情、`Esc` 关掉详情之后回到列表，选中行不变。

## 1. `agent` 工具卡片

使用 `renderShell: "self"`（`extensions/types.ts:615`），自己画框架，不要 pi 默认的彩色背景框。这样和 pi-bettertui 压缩过的工具行风格一致；
没装 pi-bettertui 时也能正常显示。

### 1.1 `renderCall`

```
● Agent explore · 查找鉴权相关代码
```

- `description` 优先；为空时用 `prompt` 的第一行，截到 60 列。
- 有 `model` 参数时末尾追加 `· deepseek/deepseek-flash`（模型自己指定模型很少见，值得让用户看到）。

### 1.2 `renderResult`：运行中（来自 `onUpdate` 的 `details.progress`）

```
● Agent explore · 查找鉴权相关代码 · 23s
  ├ Grep (/authenticate/ in src) · Read (src/auth/session.ts:40-120)
  └ 6 tools · turn 3 · 18.2K tok
```

- 第二行：当前正在执行的工具（最多 2 个），格式与 pi-bettertui 的工具行一致（`Read(path:range)`、`Grep(pattern in path)`、`Bash(命令前 40 列)`）。
- 第二行没有正在执行的工具时显示 `recentText` 的最后一行（模型正在写什么），暗色。
- 第三行：工具数 · 轮数 · token（input + output + cacheWrite，§3.5）。
- 排队中：`● Agent explore · 查找鉴权相关代码 · queued (2)`，只一行。
- 高度固定 3 行，不随内容抖动（同 pi-bettertui 的思考区）。

### 1.3 `renderResult`：结束后

折叠：

```
✓ Agent explore · 查找鉴权相关代码 · 14 tools · 48.1K tok · 1m12s ▸
✗ Agent general · 迁移 import 路径 · failed: 529 overloaded · 14s ▸
■ Agent explore · 查找鉴权相关代码 · stopped · 9s ▸
↻ Agent general · 迁移 import 路径 · out of turns (300) · 6m02s ▸
◔ Agent general · 迁移 import 路径 · context full · 9m40s ▸
```

`context full`（状态 `context_limit`，02 §9.1）用 warning 色 `◔`（U+25D4，"填满"的意思）。它和会回退字体的 `◐` 同在一个 Unicode 块，
按 pi-shizuku 的 `design_style.md` §3 的要求实测过：Windows Terminal 和 Arch 终端（含中文行）里都占一格、不回退字体、与 `●` `■` 对齐。

展开（`Ctrl+O`，pi 的工具展开快捷键）：

```
✓ Agent explore · 查找鉴权相关代码 · 14 tools · 48.1K tok · 1m12s ▾
  ag-1 · deepseek/deepseek-flash · 6 turns · $0.012
  ┌ prompt
  │ 找出处理 session 校验的代码……（前 6 行）
  ├ report
  │ （最终报告，按 Markdown 渲染，最多 40 行；超出显示 "… N more lines · <result 文件路径>"）
  └ transcript: …\subagents\<parentId>\<file>.jsonl
```

- 展开时显示 prompt 的前 6 行：用户可以看到父 agent 到底交代了什么，这是审查委派质量最直接的方式。
- 不显示子 agent 的工具调用列表：要看过程就打开详情浮层（§6）。
- **不调用 `ctx.ui.setToolsExpanded()`**（nicobailon 每次派出都会把它设成 false，覆盖用户设置）。

### 1.4 后台启动的卡片（Phase 2）

```
● Agent explore · 查找鉴权相关代码 · ag-2 running in background      运行中（accent 色，与工具行运行中同形）
✓ Agent explore · 查找鉴权相关代码 · 4 tools · 4.4K tok · 8s ▸     回复后，与前台卡片同形
✗ Agent explore · 查找鉴权相关代码 · failed · 529 overloaded · 14s
■ Agent explore · 查找鉴权相关代码 · stopped after 2s               warning 色（没跑完，但不是失败）
```

**卡片跟随 agent 的真实状态更新**（2026-11-11 修订，原设计是「之后不再更新」）。

- 原设计的理由是「进度看 HUD，结果看通知」。但被父 agent 停掉的后台 agent 不发通知（docs/06 §5.2），
  卡片就永远停在 `running in background`，回看历史时是一句假话。
- 卡片在渲染时用 `manager.get(agentId)` 推导状态，不再只看工具返回的第一份结果；`manager.subscribe` 在状态进入终态时调卡片的 `invalidate`。
  运行中的进度仍然只在 HUD 里显示，卡片只在终态变化时重画一次。
- resume 时 manager 已经从持久化的 agent 条目恢复了记录，卡片照样能查到终态；查不到（记录被清理）时显示原始的 `running in background` 文案，改成 `dim`。
- 主要使用 fullscreen 模式，卡片滚出视口后的重画不是问题；非 fullscreen 下已经进了终端回滚区的行改不了，接受。

**按运行（run）查终态**：同一个 agent 可以被 `agent_send` 重新唤起，manager 里的记录只代表最新一次运行，旧卡片不能直接用它。

1. 启动结果的 `details.run` 记下这张卡片启动的是第几次运行（`record.runs`）。
2. manager 为每个 `(agentId, run)` 保留终态快照（`runOutcome(agentId, run)`）：运行中在 `finish` 进入终态时记下，早于通知订阅者；
   restore 时从全部持久化条目里取每次运行的最后一条，仍处于活跃、被 restore 关成 `session ended` 的那次也算。
3. 卡片的那次运行还在进行时看实时记录，结束后看这份快照，不依赖渲染时的缓存。只有该次运行确实查不到时才退回 dim 的原始文案；
   没有 `details.run` 的旧结果仍按最新记录显示。
4. 卡片通过每个扩展实例一个的 `CardLink` 拿到 manager：`session_start` 在 restore 之后接上并重画已注册的卡片（resume、`/reload` 时卡片可能先于 `session_start` 画出），
   `session_shutdown` 在 manager 关停之后断开。

实现时的差异：

- 排队中的后台卡片沿用前台排队卡片的 muted `●`，排队位置是启动时的位置，之后不更新。
- 只有 completed、out of turns 和 context full 的卡片带 `▸`、可以展开（展开内容同前台卡片）；failed 和 stopped 只有一行，与上面的示例一致。
- restore 关闭的运行（原因 `session ended`）结束时间是 restore 的时刻，时长没有意义，显示成 `stopped · session ended`。
- 重启后展开已完成的卡片时，报告从 result 文件读取。被 `agent_send` 再次运行过的 agent，它的 result 文件已经换成了最新一次的报告（旧的改名为 `.result.N.md`，条目里的路径没有更新），所以旧卡片展开看到的是最新一次的报告。同一个进程里不受影响：快照里带着报告原文。

**运行中的图标用 `●`（accent 色）**：`◐`（U+25D0）和 nerd font 的 nf-fa-adjust（U+F042）都试过，前者回退字体、显示成偏大的彩色半圆，
后者是 Font Awesome 字形，在非 Mono 版 nerd font 里比一格宽、压到后面的字，笔画也比 `✓` `×` 重。`●` 是工具行已经在用、在用户字体里验证过的字形，和工具行「运行中 ● → 完成 ✓/●」的语言一致；HUD 与详情浮层同改。

**`Agent Stop` 行改成 `dim`**：停止的结果已经由被停 agent 的卡片（warning 色 `■`）表达，`Agent Stop` 只是一个动作，不再用绿色 `●` 和它抢。

## 3. HUD 里的 agent 行（Phase 2）

### 3.1 位置与样式

放在 pi-hud 第三行（工具行）**下面**，与 claude-hud 的布局一致：

```
[deepseek/deepseek-pro | high] | demo-app git:(main) | 1 shell
Context ███░░░░░░░ 25% (1M) | 200 tps · 30.0M token used · agents 120K
✓ Bash ×16 | ✓ Write ×2 | ✓ Edit ×2
● explore [flash]: 查找鉴权相关代码 (1m 12s · turn 4)
● general: 迁移 import 路径 (2m 10s · turn 9)
◌ explore: 检查迁移脚本 (queued)
✓ explore: 统计配置项 (48s)
… +2 more agents
```

为什么必须由 pi-hud 来画：pi 的界面从上到下是 编辑器 → belowEditor widget → footer（`interactive-mode.ts:1012-1013`），
widget 只能放在编辑器上方或下方，**放不到 footer 下面**。pi-hud 就是 footer（`ctx.ui.setFooter`），所以这几行只能是 pi-hud 输出的一部分。

每行格式参照 claude-hud 的 `agentsLine`（`refs/claude-hud/src/render/activity.ts:109-122`）：

```
<图标> <类型>[ <模型简称>]: <description> (<时长>[ · <细节>])
```

| 部分 | 规则 |
|---|---|
| 图标 | `●` 运行（accent 色）、`◌` 排队（dim）、`✓` 完成（success）、`✗` 失败（error）、`■` 已停止（warning，见 pi-shizuku 的 `design_style.md` §3）、`↻` 轮数耗尽（warning）、`◔` 上下文满（warning） |
| 类型 | accent 色（claude-hud 用 magenta） |
| 模型简称 | **只在与父会话模型不同时**显示，取 `id` 去掉 provider 前缀，例如 `[flash]` |
| description | 截断优先级最高：终端变窄时先截它，最短保留 12 列 |
| 时长 | 格式同 claude-hud 的 `formatElapsed`：`<1s`、`48s`、`2m 10s`、`1h 3m` |
| 细节 | 运行中：`turn N`；失败：原因前 30 列；轮数耗尽：`out of turns`；上下文满：`context full` |

前台和后台 agent 都显示：前台 agent 在工具卡片里也有进度，但 HUD 是统一的入口，点进去看详情的方式一致。

第一行不再显示 `· 2 agents` 计数：有 agent 行时计数是重复信息。第二行的 `agents 120K` 保留（用量汇总，§3.5）。

### 3.2 显示哪些行

由 pi-subagent 决定，pi-hud 只负责画（§3.3）。

**平时**（没有键盘焦点）：

1. 所有 `running` / `queued` 的，按开始时间排序。
2. 加上 60 秒内结束的（claude-hud 的 `COMPLETED_RETENTION_MS`），按结束时间倒序。
3. 总共最多 **4 行**；超出时追加一行 `… +N more agents`。
4. 没有可显示的行时，这一块不占任何高度。

和 claude-hud 的区别：claude-hud 最多 3 行、已完成的最多 2 行、只显示 completed。我们把失败、停止的也显示出来：后台 agent 失败是最需要被看到的状态。

**有键盘焦点时**（§4）：

- 列出本会话的**全部** agent（运行中的在前，其余按结束时间倒序）。
- 最多显示 **8 行**，以选中行为中心滚动；上下有隐藏的行时，首尾各显示 `↑ N more` / `↓ N more`。
- 末尾加一行提示：`↑↓ select · enter view · x stop · esc back`；按下第一次 `x` 后整行换成 error 色的
  `press x again to stop · any other key cancels`（§4.4）。
- 选中按 `agentId` 跟踪，不按下标：列表在你移动的同时可能因为有 agent 结束而重新排序。
- 已经请求停止、但运行还没返回的 agent，时长后面显示 `stopping` 而不是轮数。

### 3.3 pi-subagent ↔ pi-hud 协议

全部走 `pi.events`（同步分发，见 bg-shell DESIGN §1.1），沿用 `bg:state` / `bg:state:request` 的模式。两个插件不互相 import。

**pi-subagent → pi-hud**

```ts
// 状态变化时发；收到 "subagent:state:request" 时重发；session_shutdown 时发空状态
"subagent:state": {
  rows: AgentRow[];          // 已经按 §3.2 过滤、排序、开窗，pi-hud 原样画
  above: number;             // 焦点模式下上方隐藏的行数（平时为 0）
  below: number;             // 下方隐藏的行数；平时即 "+N more agents" 的 N
  focus: { selectedId: string; armed?: true } | null;  // armed：选中行按过一次 x，等第二次（§4.4）
  tokens: number;            // §3.5
  cost: number;
}

interface AgentRow {
  id: string;                // ag-3
  type: string;
  description: string;
  status: "queued" | "running" | "completed" | "failed" | "aborted" | "max_turns" | "context_limit";
  startedAt?: number;        // 排队中没有
  endedAt?: number;
  turn?: number;             // 运行中；已请求停止时不给
  model?: string;            // 只在与父会话模型不同时给出，已是简称
  detail?: string;           // 失败原因等，已截短；已请求停止、运行还没返回时是 "stopping"
}
```

运行中的时长由 pi-hud 用 `Date.now() - startedAt` 自己算。有运行中的行时，pi-hud 开一个 1 秒的定时器调用 `tui.requestRender()`；
没有时关掉。pi-subagent 只在状态变化时发事件，不按秒发。

**pi-hud → pi-subagent**

```ts
// footer 装上或卸下时发（session_start、/hud on、/hud off、model_select 重建 footer 时），
// 以及收到 "subagent:hud:request" 时
"subagent:hud": { rendering: boolean }

// 鼠标点击 agent 行时发（§5）；点击 "+N more" 或 "↑/↓ N more" 行时不带 agentId
"subagent:open": { agentId?: string }
```

`rendering` 为 false（pi-hud 没装，或 `/hud off`）时，pi-subagent 不进入键盘焦点模式（没有东西可以高亮），
只剩 `/agents` 入口（§7）。

### 3.4 pi-hud 的改动

| 改动 | 位置 | 估计 |
|---|---|---|
| 订阅 `subagent:state`，发 `subagent:state:request`（照 `bg:state` 的写法） | `pi-hud src/index.ts` | 20 行 |
| 发 `subagent:hud`；响应 `subagent:hud:request` | `index.ts` 的 `apply()` | 10 行 |
| `renderAgentRows(state, theme, width)`：画行、选中行的竖标和选中底色、提示行 | `pi-hud src/render.ts` | 60 行 |
| 渲染时记录"第几行 → 哪个 agent"的映射，供点击使用 | footer 组件 | 10 行 |
| footer 组件实现 `handleMouse`（§5） | footer 组件 | 15 行 |
| 有运行中的行时每秒重绘 | footer 组件 | 10 行 |
| 第一行去掉 agent 计数；第二行加 `agents 120K` | `render.ts` | 10 行 |

实现时的差异（Phase 2）：

- `renderAgentRows` 和点击映射放在新文件 `pi-hud src/agents.ts`（纯函数，pi-hud 因此加了 vitest），`render.ts` 只加了 `agents` 用量段。
- pi-hud 第一行本来就没有 agent 计数，无需删除。
- 第二行降级时，`agents 120K` 和会话总量一起保留到倒数第二步（只剩 tps 和总量那一步），最后一步才去掉。
- 每秒重绘的定时器只在"footer 已挂载且有 running 行"时存在。

pi-hud README 已经为此留了口子：嵌套调用"后续接 subagent 时它们应该归到 agent 行"（`pi-hud README.md:57`）。
子 agent 的工具调用发生在子会话里，根本不会出现在父会话的事件流中，所以 pi-hud 的工具行不需要任何过滤改动。

### 3.5 用量口径

- **token**：input + output + cacheWrite，**不算 cacheRead**。cacheRead 是每一轮重复读同一段缓存前缀，累加起来会把一个 30 轮的子 agent 算成几十万 token（gotgenes `usage.ts`）。
- **cost**：直接累加 `usage.cost.total`，pi-ai 已按模型目录算好（`pi/packages/ai/src/types.ts:467-493`）。cost 包含 cacheRead 的费用，这是真实花费。
- 子 agent 的用量**不**并入父会话的 `token used`：两者口径不同（pi-hud 的会话累计取自父会话 branch 上的 assistant 消息），混在一起会让上下文用量和花费都看不懂。

## 4. 键盘焦点（Phase 2）

### 4.1 机制

`ctx.ui.onTerminalInput(handler)` 注册的监听器会在**编辑器之前**拿到每一个按键，返回 `{ consume: true }` 就把这个键吞掉
（`pi/packages/tui/src/tui.ts:1095-1110`，编辑器在 `:1158` 才收到）。pi 在 `/reload` 后会自动重新绑定这些监听器（`interactive-mode.ts:2702`）。

焦点状态完全在 pi-subagent 内部：编辑器的光标照常留在原处，"焦点"的唯一视觉表现是 HUD 里的选中行（左栏 accent 竖标 `▎` 加铺满整行的主题选中底色）和提示行。

### 4.2 按键

| 状态 | 按键 | 行为 | 吞掉？ |
|---|---|---|---|
| 未聚焦 | `↓`，且编辑器为空、HUD 在渲染、有可显示的行 | 进入焦点模式，选中第一行 | ✅ |
| 未聚焦 | 其他 | 不处理 | ❌ |
| 聚焦 | `↑` | 上一行；已在第一行则退出焦点模式 | ✅ |
| 聚焦 | `↓` | 下一行；已在最后一行则不动 | ✅ |
| 聚焦 | `Enter` | 打开详情浮层（§6）；关闭浮层后回到焦点模式，选中行不变 | ✅ |
| 聚焦 | `x` | 选中的 agent 运行中或排队中、且还没请求过停止时：第一次进入确认态，第二次停止它，等同面板停止：会通知模型（06 §5.2）。确认态下的按键见 §4.4；`confirmStop` 关掉时一次就停 | ✅ |
| 聚焦 | `Esc` | 退出焦点模式 | ✅ |
| 聚焦 | 按键释放事件（`isKeyRelease`） | 忽略 | ✅ |
| 聚焦 | 其他任何键 | 退出焦点模式，**不吞**，原样交给编辑器 | ❌ |

最后一条保证你在焦点模式下直接开始打字，第一个字符不会丢。

**为什么是 ↓**：全屏模式下 HUD 就在编辑器正下方，"往下移进 HUD"在空间上是直觉的。编辑器的 ↓ 只用于翻历史，
不在翻历史时按 ↓ 什么也不做（`pi/packages/tui/src/components/editor.ts:465-466`）；编辑器为空就说明没在翻历史（历史条目都非空），
所以这个手势不会抢走任何现有功能。全屏模式自己只占用 PageUp / PageDown（`tui-alt-screen.ts:763`），也不冲突。

### 4.3 必须处理好的坑

| 坑 | 后果 | 对策 |
|---|---|---|
| **Esc 冲突** | pi 里 Esc 是中断主 agent。焦点模式下不吞 Esc，想退出列表却中断了主 agent；反过来，焦点状态卡住不退出，Esc 就永远中断不了主 agent | 焦点模式下吞 Esc。退出条件做全：可显示的行变为 0、HUD 不再渲染（`subagent:hud` 为 false）、`session_shutdown`、编辑器文本非空（每次按键时检查）、焦点模式下 30 秒无按键 |
| kitty 键盘协议的释放事件 | 一次按键触发两次移动 | `isKeyRelease` 过滤 |
| 自动补全弹窗 | ↓ 本来要选补全项 | 补全弹窗只在编辑器有内容时出现，"编辑器为空"已经排除 |
| 其他扩展的输入监听器 | 按注册顺序依次调用，前面的可能先吞掉 ↓ | 目前你的插件里没有别的键盘监听器（pi-bettertui 只有鼠标处理）；以后加了要注意 |
| **对话框 / 选择器 / 浮层拿着键盘**（实现时发现） | `onTerminalInput` 的监听器在任何组件之前拿到按键，包括 pi 自己的模型选择器、扩展对话框、浮层获得焦点时（`tui.ts:1095-1110` 在焦点分发之前）。这时编辑器仍然为空，↓ 会被抢走 | 多一个条件"编辑器有焦点"：进入时检查，焦点模式下每次按键也检查，不满足就退出且不吞。实现：注册一个 0 行的 `belowEditor` widget，拿它工厂参数里的 `tui`（`interactive-mode.ts:641` 的代理，换渲染器也有效），用 `getFocusedComponent()`（`tui.ts:623`，在 `TuiBase` 上，不在公开的 `TUI` 接口里，所以按鸭子类型调用）判断焦点组件有没有 `getText`（编辑器有，选择器和对话框没有）。本插件自己的列表或详情浮层打开时也视为编辑器没有焦点 |

另外，鼠标序列（`\x1b[<…`）在焦点模式下既不处理也不退出：全屏模式下它们由 alt-screen 自己的输入监听器先吞掉（`tui-alt-screen.ts:282` 在构造时注册，早于扩展），扩展本来看不到，这里只是防御。

`matchesKey`、`isKeyRelease` 从 `@earendil-works/pi-tui` 导出（`pi/packages/tui/src/index.ts:100, 106`）。

### 4.4 停止确认：`x x`

**问题**：`x` 一按就停，停掉的 agent 已经烧掉的轮数和上下文都没法恢复。`x` 又紧挨着常用键，在列表里手滑一下代价太大。

**方案取舍**：

| 方案 | 好处 | 代价 |
|---|---|---|
| 不确认 | 最快 | 手滑即损失 |
| `x` 后按 `y` 确认 | 和 y/n 对话框一致 | 手要换位置；`y` 在这些界面里没有别的用处，读起来像弹了一个对话框，太重 |
| `x` 后再按一次 `x`（同 vim 的 `dd`） | 手指不动；提示一句话就讲清楚 | 按住 `x` 时键盘自动重复会连发两次。自动重复要按住约 0.25–0.5 秒才开始，实际不容易误触，不做防抖 |

选 `x x`。在三处入口统一生效：HUD 焦点模式（§4.2）、详情浮层（§6）、`/agents` 列表（§7）。

**确认态长什么样**：

- 选中行：竖标从 accent 换成 `error` 色，选中底色从 `selectedBg` 换成 `toolErrorBg`（主题里已有的错误类底色，明度和 `selectedBg` 同级，
  所以选中行里弱化文字升 `muted` 的规则照样适用）。不自己算"深一级"的颜色：深浅主题方向相反，算出来的颜色在一边会更不显眼。
- 提示行：整行换成 error 色的 `press x again to stop · any other key cancels`，而不是只替换其中的 `x stop` 一段。
- 详情浮层没有选中行，只换底部提示行。

**确认态下的按键**：

| 按键 | 行为 |
|---|---|
| `x` | 停止，回到普通选中；行上显示 `stopping`，运行返回后变成 `stopped` |
| `↑` `↓`（详情里还有 `PageUp` `PageDown` `Home` `End` 和滚轮） | 取消确认，**照常移动**；焦点模式第一行按 `↑` 照常退出焦点模式 |
| `Esc` | **只取消**，不关列表、不关浮层、不退出焦点模式 |
| `Enter` | **只取消**，不打开详情：手指正处在"确认"的状态，`Enter` 很可能是下意识按的 |
| 其他任何键（包括焦点模式下打字） | **只取消并吞掉**。焦点模式平时会把这类键交给编辑器并退出，确认态下不这样：打出去的字落进输入框，人往往不知道自己已经退出了焦点模式 |

**确认绑在 agent id 上，不绑行号**。列表每秒重排，焦点模式在 agent 集合变化时会重新选中；绑行号的话，第二次 `x` 可能停掉挪到这一行的另一个 agent。
下面任一情况发生，确认自动取消：

- 那个 agent 自己结束了，或者别处（`agent_stop`）已经请求停止它；
- 它从列表里消失了；
- 选中项变了；
- 列表、浮层关闭，焦点模式退出（包括 30 秒无按键超时）。

**不加超时**。vim 的 `dd` 等第二个 `d` 也没有超时；确认态在视觉上足够醒目，挂着也不会被忽略。
有超时反而会出现"第二次按慢了，结果又进了一次确认"。

**已请求停止的 agent 不能再确认**。停止是异步的：运行要在几秒内返回部分报告，期间状态仍是 running。
记录上有 `stoppedBy` 就算已请求，这段时间里 `x` 什么也不做，列表和详情标题显示 `stopping`，HUD 行在时长后显示 `stopping`，提示行不再给 `x stop`。

**开关**：`~/.pi/agent/pi-subagent.json` 的 `confirmStop`，默认 `true`；设为 `false` 回到一次就停。每次按 `x` 时读取，`/agents reload` 后生效。

## 5. 鼠标点击（Phase 2）

- 全屏模式把鼠标事件路由给点击位置下的组件；普通模式下鼠标归终端（`pi/packages/coding-agent/docs/tui.md` "Handle mouse input"）。所以这一节只在全屏模式下生效，键盘路径（§4）始终可用。
- 路由路径：alt-screen 按屏幕坐标找到布局里的组件（`tui-alt-screen.ts:847-865`），`Container.handleMouse` 再按行把事件分给子组件，
  并把 `y` 换算成子组件内部的行号（`tui.ts:389-408`）。pi-hud 的 footer 组件实现 `handleMouse` 就能收到点击和它在 HUD 里的行号。
  pi-bettertui 的工具行已经这样用了（`pi-bettertui src/tool-row.ts:100-108`）。
- pi-hud 的处理：

  ```ts
  handleMouse(event) {
    if (event.type !== "click" || event.button !== "left") return undefined;
    const target = rowTargets[event.y];                 // 渲染时记录的 行号 → agentId | "more"
    if (target === undefined) return undefined;        // 点在前三行：不处理，交给默认行为（例如文本选择）
    pi.events.emit("subagent:open", target === "more" ? {} : { agentId: target });
    return { handled: true };
  }
  ```

- pi-subagent 收到 `subagent:open`：有 `agentId` → 打开该 agent 的详情浮层；没有 → 在底部打开 `/agents` 列表（§7）。
  - 已有详情浮层：再来的请求（不论有没有 `agentId`）都忽略。
  - 列表已经打开：有 `agentId` → 详情浮层叠在列表上面，关闭后回到列表；没有 `agentId`（`+N more`）→ 忽略。
- 详情浮层里的滚轮滚动由浮层组件自己的 `handleMouse` 处理（`type: "wheel"`，按 `wheelDelta` 滚动），不是 `ScrollView`，见 §6。
- **已核对（读代码）**：全屏下点击 HUD 的完整路径是 alt-screen 的输入监听器解析 SGR 鼠标序列（`tui-alt-screen.ts:735-738`）→ `handleMouseEvent`（`:915`）。
  按下（press）时 footer 返回 `undefined`，于是走文本选择逻辑记下锚点（`:1391-1411`）；松开时位置没变就合成一个 `click`，
  再 `dispatchMouseToLayout`（`:1365-1375`）。`getLayoutBoxesAt` 按深度从深到浅返回盒子（`layout.ts:419-428`），
  `footerContainer` 是普通 `Container`（不是 layout node，`layout-node.ts:48-51`），于是 `Container.handleMouse` 把 `y` 换算成子组件内的行号交给 pi-hud 的 footer（`tui.ts:389-408`）。
  返回 `{ handled: true }` 之后 alt-screen 清掉选择、不复制（`:1371-1374`）。所以伪代码里"只处理 `click`、press 返回 `undefined`"是对的。
  **仍需在真实全屏会话里手动点一次确认**（终端的鼠标上报、行号偏移只能在真实终端里看到）。
- footer 在全屏布局里是 `shrink: 1`（`chat-viewport.ts:37`）：屏幕很矮时 footer 会被裁掉一部分，点击映射按渲染输出的行号算，被裁掉的行本来也点不到。

## 7. `/agents` 命令

| 用法 | 作用 | 阶段 |
|---|---|---|
| `/agents types` | 列出已加载的类型：名字、来源（内置 / 用户 / 项目）、模型、工具；以及加载告警（04 §7） | Phase 1 |
| `/agents reload` | 重新加载类型文件和配置（04 §6） | Phase 1 |
| `/agents` | 在底部打开列表：本会话全部 agent，`↑↓` 选择、`Enter` 进详情（§6）、`x x` 停止、`Esc` / `q` 关闭；非 TUI 模式下 `ctx.ui.notify` 一段文字列表 | Phase 2 |

列表是 HUD 入口的备用：pi-hud 没装、`/hud off`、或者 agent 太多想一次看全时使用。点击 HUD 的 `+N more` 行也打开它。

- 位置：不带 `overlay` 的 `ctx.ui.custom`，占编辑器的位置（理由见文首"选择列表在底部，长内容详情用浮层"）。打开期间主 agent 照常运行；
  关闭后 pi 恢复编辑器和其中原来的文字。
- 高度：pi 不限制编辑器位置组件的高度，所以列表自己限高：一次最多显示 `min(10, 终端行数 × 40%)` 个 agent（至少 3 个），
  其余用 `↑ N more` / `↓ N more` 提示，选中行移动时窗口跟着走。
- `Enter`：详情浮层叠在列表上面，列表不关；详情里 `Esc` / `q` 只关详情，回到列表，选中行不变。列表里 `Esc` / `q` 关列表。
- `x x`：停止选中的运行中 agent，第一次 `x` 只进入确认态（§4.4）；确认态下 `Esc` / `q` / `Enter` 只取消，不关列表、不开详情。
- 列表打开时它拿着键盘，↓ 不会进入焦点模式（§4）；HUD 里点击 agent 行照样打开详情（叠在列表上），点击 `+N more` 被忽略。

选中行用两层标记：行首的 accent 竖标 `▎`，加上铺满整行的主题选中底色（`selectedBg`）。
和 `/background` 列表、HUD 焦点模式选中行是同一套写法（约定见 `pi-hud/DESIGN.md` §2.1）；底色上的弱化文字用 `muted`，否则比终端背景浅的底色会让它糊掉。

## 8. 与 pi-bettertui 的关系

- pi-bettertui 只把连续的 `read/grep/find/ls` 合并成组，未知工具永远不合并（`pi-bettertui README.md` "只合并只读探索"）。`agent` 是未知工具，单独成行，符合预期。
- pi-bettertui 的轮次结束行 `Worked for 2m 5s · 7 tools`：`agent` 计为 1 个工具，子 agent 内部的工具不计入。不改。
- pi-bettertui 覆盖了 `bash` / `powershell` 以加 `description` 参数；子会话不加载扩展，用的是 pi 原生 bash（04 §3.2）。
  详情浮层的 Activity 行因此拿不到 `description`，显示命令本身（中间省略，规则同 pi-bettertui）。
- 工具行的单行格式（`Read(path:range) · N lines` 等）在工具卡片（§1.2）和详情浮层（§6）里都要用到。先在本插件里写一份；
  如果和 pi-bettertui 的实现几乎一样，再考虑抽到共享位置（同 08 §2 的思路）。
